# Fase 7b — Akun (Rekonsiliasi, Piutang/Hutang + Kontak) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- ACC-04: **rekonsiliasi** akun. User memasukkan saldo riil per tanggal. App membuat transaksi `adjustment` sebesar selisihnya (kalau ada), lalu menandai posting akun itu sampai tanggal tersebut sebagai `reconciled`.
- D10(b): jenis akun **Piutang/Hutang** dengan **kontak**. Satu akun mewakili saldo piutang/hutang dengan satu orang. Saldo positif berarti piutang (aset), saldo negatif berarti hutang (liabilitas).

**Architecture:**
- `nabungo-core`: aturan klasifikasi `AccountKind::counts_as_liability(balance)`, dipakai `net_worth` dan `allocation_report`. Tidak ada jenis akun baru.
- `nabungo-storage`: migrasi `0006_contact.sql` menambah tabel `contact` dan kolom `account.contact_id`. Repository `contact.rs`. `mark_reconciled` dan `reconciled_through` memakai kolom `posting.reconciled` yang sudah ada sejak `0001`. Baris daftar transaksi mendapat field `reconciled` saat difilter per akun.
- `nabungo-app`: `AccountFields.contact` (nama kontak, dibuat bila belum ada) dan `list_contacts`. File baru `reconcile.rs` berisi `reconcile_account`, mengikuti pola `valuation.rs`.
- `src-tauri`: perluasan DTO, command `reconcile_account` dan `list_contacts`.
- UI: dialog Rekonsiliasi; form akun Piutang/Hutang dengan kontak dan arah saldo; label Piutang/Hutang di daftar akun; ikon reconciled di daftar transaksi. `browser-ledger.ts` mencerminkan semua aturan.

**Tech Stack:** Rust (crate yang sudah ada, tanpa dependensi baru), Vue 3 + shadcn-vue (komponen yang sudah ada), Vitest, Playwright.

**Spec:**
- `PRD.md`: D10, tabel jenis akun (Receivable, Bank "mendukung rekonsiliasi"), tabel jenis transaksi (Adjustment), ACC-04, invariant §6 no. 3 (adjustment tanpa kategori), aturan basis alokasi (aset bruto, liabilitas terpisah), layar Detail akun ("tombol Rekonsiliasi").
- Roadmap: `docs/plans/2026-10-12-v1-roadmap.md` Fase 7.
- Desain: `docs/design/ui-guidelines.md` §9.3 (Akun), §8.5 (baris transaksi), §8.9 (dialog).

**Di luar plan ini:** layar detail akun dengan grafik saldo (Fase 7e/RPT); rename/merge/hapus kontak; batal rekonsiliasi (unmark).

Tidak ada jenis `payable`. | Menambah jenis berarti mengubah CHECK `account.kind`. Piutang dan hutang ke orang yang sama juga saling meniadakan, jadi cukup satu akun per orang. |
| K2 | `AccountKind::counts_as_liability(self, balance: i64) -> bool` = `is_liability()` atau (`Receivable` dan `balance < 0`). `net_worth` dan `allocation_report` memakai fungsi ini sebagai pengganti `is_liability()`. | K3 | Kontak = tabel `contact(id, name UNIQUE COLLATE NOCASE, created_at, updated_at)`, ditambah `account.contact_id` nullable FK. `AccountFields.contact: Option<String>` berisi **nama**. Saat simpan, nama di-trim lalu `normalize_name`. Kosong menjadi `None`. Nama yang sudah ada (NOCASE) dipakai ulang; kalau belum ada, kontak dibuat. Untuk jenis selain `receivable`, nilainya dibuang diam-diam (pola yang sama dengan `credit_limit` pada non-kartu-kredit). | Minimal: kontak hanya identitas orang, dan kontak yang sama bisa dipakai ulang lewat saran nama. |

## Global Constraints

- Arah dependensi tetap: `ui → src-tauri → nabungo-app → (nabungo-core, nabungo-storage)`. `src-tauri` tanpa logika bisnis.
- `nabungo-core` tanpa IO dan tanpa float. Nominal `i64`.
- Migrasi `0001`–`0005` tidak diubah. Migrasi baru `0006_contact.sql` didaftarkan di `migrations()` di `crates/storage/src/lib.rs`.
- Repository tulis menerima `&Transaction`; baca boleh `&Connection`. Satu use case tulis = satu SQLite transaction.
- Saldo, net worth, porsi alokasi, dan `reconciled_through` diturunkan dari `posting`; tidak ada kolom saldo.
- `browser-ledger.ts` harus memberi hasil yang sama dengan Rust untuk K2, K3, K5, K6, K9, dan K10.
- Kode error baru wajib masuk `errors` di `ui/src/i18n/id.ts` dan `en.ts`. Plan ini **tidak** menambah kode error (memakai `not_found`, `archived`, `txn_amount_too_large`, dan kode `catalog` untuk nama kontak yang sudah ada).
- `ui/src/ipc/bindings.ts` di-generate (`cargo test -p nabungo-desktop export_bindings`) dan di-commit.
- UI mengikuti `docs/design/ui-guidelines.md`: angka `num` rata kanan, dialog shadcn `Dialog`, teks bahasa Indonesia di `id.ts` dan padanannya di `en.ts`.
- Verifikasi akhir tiap task Rust: `cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings`.

## Review Focus

1. **Receivable bersaldo negatif** (hutang) harus masuk liabilitas di net worth, laporan net worth bulanan, dan alokasi (tidak menambah `gross`), baik di Rust maupun browser-ledger. Test: Task 1 `negative_receivable_is_liability`, `allocation_skips_negative_receivable`; Task 6 `hutang dihitung sebagai liabilitas`.
2. **Rekonsiliasi dengan transaksi sesudah tanggal rekonsiliasi.** Selisih dihitung terhadap saldo per `date`, bukan saldo hari ini, dan posting setelah `date` tidak ditandai. Test: Task 4 `difference_uses_balance_as_of_date`, `later_postings_stay_unreconciled`.
3. **Saldo sudah cocok** (selisih 0) tidak boleh membuat txn adjustment nol, dan bukan error. Test: Task 4 `matching_balance_marks_without_adjustment`.
4. **Nama kontak beda huruf besar/kecil atau ada spasi** ("budi " vs "Budi") memakai kontak yang sama, bukan duplikat atau error UNIQUE. Test: Task 3 `contact_reused_case_insensitively`.
5. **Edit transaksi yang sudah reconciled** mengembalikan flag menjadi tidak reconciled, dan `reconciled_through` turun mengikutinya. Test: Task 2 `replace_txn_clears_reconciled`.
