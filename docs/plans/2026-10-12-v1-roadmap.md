## Fase 0 — Scaffold (selesai)

- Cargo workspace: `crates/core`, `crates/storage`, `crates/app`, `src-tauri`; pnpm workspace dengan `ui/`.
- Migrasi `0001_init.sql` = skema PRD §6 + seed IDR. Test storage: migrasi valid, FK aktif, tabel inti ada.
- UI: Vue 3 + TS + Vite + Tailwind v4 + shadcn-vue (button, card, sonner), Pinia, vue-router, vue-i18n (id/en), font lokal. Command `app_version` sebagai smoke test end-to-end.
- CI: fmt, clippy `-D warnings`, test Rust (Linux + Windows), typecheck/test/build UI.

**Exit criteria (belum diverifikasi — butuh `gcc` + dependency Tauri):**
- `cargo test --workspace` hijau, `cargo clippy --workspace --all-targets -- -D warnings` bersih.
- `pnpm dev` membuka jendela Nabungo dan kartu dasbor menampilkan `core v0.1.0`.
- Commit awal dibuat.

## Fase 1 — Fondasi domain & storage

Tujuan: semua aturan uang yang tidak boleh salah sudah terkunci oleh test sebelum ada UI.

- `core`: `Money`/`CurrencyCode`, helper tanggal `YYYY-MM-DD`, `period_of(date, start_day)`, enum `AccountKind`/`CategoryKind`/`TxnKind`, `TxnDraft` + `validate()` untuk invariant 1–3.
- `storage`: repository akun, kategori, transaksi (header + postings dalam satu SQLite transaction), query saldo dari postings, soft delete.
- `app`: `Ledger` (create account + opening balance otomatis, record, delete/undo, balance).
- Property test: ribuan transaksi acak → saldo = model; total saldo tetap pada transfer.

**Exit:** semua test fase 1 hijau; tidak ada `f64` di `core` (dijaga lint).

## Fase 2 — IPC & app shell (selesai)

- `tauri-specta` → binding TS ter-generate di `ui/src/ipc/bindings.ts`; hapus `invoke` manual.
- State Tauri: satu koneksi tulis di `Mutex` + pool kecil koneksi baca (WAL). Lokasi data via `directories` (`~/.local/share/nabungo/`, `%APPDATA%\nabungo\`), mode portable opsional.
- Error domain bertipe → DTO error → pesan i18n di UI.
- Layout 2 kolom (shadcn `Sidebar`), router untuk semua layar PRD §9 (placeholder), command palette `Ctrl+K`, shortcut `N`, `G D/T/B/A/R`, `Ctrl+,`.
- Tema terang/gelap + token warna semantik (income/expense/transfer).
- Parser input nominal: ekspresi `25000+12500`, sufiks `rb`/`jt` (`1,5jt`) — di Rust `core` agar satu sumber kebenaran, dengan test tabel.
- Logging `tracing` + `tracing-appender` ke folder data, tanpa telemetry.

**Exit:** navigasi keyboard penuh antar layar kosong; CSP tidak memblokir apa pun yang dipakai app; binding TS ter-generate otomatis.

**Keputusan saat eksekusi:**
- Pool koneksi baca ditunda ke Fase 5 (laporan/budget adalah query berat pertama); Fase 2 cukup satu koneksi di `Mutex`.
- Pengaturan UI (tema, bahasa) disimpan di tabel `setting` di DB, bukan `localStorage`, agar ikut backup/pindah file.
- Mode portable: file penanda `portable` di samping executable → data di `<exe_dir>/data` (tidak berlaku untuk AppImage yang read-only).

## Fase 3 — Akun & kategori (selesai)

- ACC-01/02: CRUD akun & account group, urutan drag-and-drop, arsip (bukan hapus) bila punya transaksi.
- ACC-03: saldo per akun + net worth (aset − liability, hormati `include_in_net_worth`) di sidebar dan dasbor.
- CAT-01: seed kategori default (Makan & Minum, Transportasi, Tagihan, Belanja, Kesehatan, Hiburan, Gaji, Bonus, Biaya admin, …) saat onboarding; pohon 2 level.
- CAT-02: merge (pindahkan postings) & arsip kategori.
- CAT-03: saran kategori dari payee terakhir (`payee.default_category_id`).
- Onboarding minimal: bahasa, tanggal awal periode budget, akun pertama.

**Exit:** hapus akun/kategori terpakai diblokir dan menawarkan arsip/merge (acceptance "hapus aman").

**Keputusan saat eksekusi:**
- CAT-03: backend selesai (upsert payee saat `record`, `suggest_category`); UI saran kategori dipasang di form transaksi Fase 4.
- Akun diarsip tetap dihitung di net worth (saldo tidak hilang); yang menyaring hanya `include_in_net_worth`. UI meminta konfirmasi saat mengarsip akun bersaldo ≠ 0.
- Arsip kategori parent ikut mengarsip child; pulihkan child ditolak selama parent masih diarsip.
- Merge kategori memindahkan postings dan budget (budget periode yang sama dijumlahkan) lalu menghapus source.
- Saldo awal diedit lewat form akun (transaksi `opening` ditulis ulang); `record` menolak `TxnKind::Opening`.
- Exit "hapus aman" dikunci test view (`AccountsView.test.ts`, `CategoriesView.test.ts`) dan test app (`InUse`). Cek manual di jendela Tauri belum dilakukan di sesi eksekusi — lakukan sebelum Fase 4.

## Fase 4 — Transaksi (selesai)

- TRX-01: form Income/Expense/Transfer (`Sheet` + `Tabs`), keyboard-first; expense tercatat dalam ≤ 5 interaksi dari layar mana pun.
- TRX-02: biaya admin opsional pada transfer.
- TRX-03: split ke beberapa kategori; total harus sama dengan nominal (validasi di Rust).
- TRX-04: daftar transaksi virtualized (TanStack Table + vue-virtual), filter tanggal/akun/kategori/tag/payee/nominal, pencarian teks, grouping per tanggal, saldo berjalan saat difilter per akun, paginasi di SQL.
- TRX-05: edit, duplikasi, soft delete + undo (toast Sonner).

**Exit:** test e2e Playwright/WebDriver: input expense, transfer dengan biaya, undo hapus.

**Keputusan saat eksekusi:**
- Form dikonversi ke postings oleh `form_postings` di core (bukan di UI); split yang tidak cocok → `txn_split_mismatch`, transfer ≤ 0 → `txn_not_positive`.
- Edit transaksi yang akunnya/kategorinya sudah diarsip tetap boleh selama ref itu dipakai versi lama; ref arsip baru ditolak. Transaksi `opening` hanya diubah lewat form akun.
- Kategori biaya default: kategori biaya terakhir dipakai, lalu seed "Biaya admin"/"Fees" (abaikan yang diarsip).
- Saran payee mengisi kategori dan akun yang belum disentuh user, tidak pernah menimpa pilihan user.
- Tag dinormalisasi (trim, buang `#`, dedupe tanpa beda huruf ASCII).
- TRX-04 memakai `@tanstack/vue-virtual` saja (tanpa TanStack Table); payee dicari lewat kotak pencarian (backend tetap punya filter `payeeId` untuk layar nanti). Filter nominal membandingkan `|nominal|`.
- Setelah aksi tulis, daftar dimuat ulang sebanyak baris yang sudah dimuat (posisi scroll tidak hilang saat hapus/undo).
- Combobox kategori/payee dan input tag dibuat sendiri (bukan shadcn combobox) agar perilaku keyboard teruji di jsdom dan Ctrl+Enter sampai ke form.
- Mode browser (`pnpm --filter @nabungo/ui dev`, e2e): parser nominal di-port ke `ipc/browser-amount.ts` dengan tabel uji yang sama dengan Rust.
- E2E (`pnpm --filter @nabungo/ui e2e`) berjalan di browser terhadap browser-ledger, bukan jendela Tauri. Cek manual di jendela Tauri (DB nyata) belum dilakukan di sesi eksekusi — lakukan sebelum Fase 5.

## Fase 5 — Budget, alokasi modal, laporan (selesai)

- BUD-01: limit bulanan per kategori expense, salin dari bulan lalu; realisasi memakai `period_of` + rentang tanggal periode, termasuk child category; refund mengurangi realisasi; transfer tidak memengaruhi budget (test eksplisit).
- CAP-01..03: bucket bertingkat (target relatif ke parent), mapping akun dengan `share_bp`, validasi total ≠ 100% dan daftar "Belum dialokasikan".
- CAP-04: transaksi Valuation untuk akun investment + riwayat nilai.
- CAP-02: donut porsi aktual, tabel target vs aktual vs selisih (poin % dan rupiah), riwayat porsi bulanan; basis gross aset.
- RPT-02: income vs expense per bulan, breakdown kategori, tren 12 bulan (agregasi di SQL).
- RPT-03: net worth over time dari postings + valuation.

**Exit:** semua acceptance criteria MVP di PRD §5 lulus. → **Gate 1**.

**Keputusan saat eksekusi** (detail K1–K12 di plan Fase 5):
- "Bulan" di Budget, Laporan, dan riwayat Alokasi = periode budget (K1). Realisasi parent = parent + child; total budget hanya menjumlah baris teratas agar tidak ganda (K2). Budget 0 valid, hapus = `None` (K3). Salin dari bulan lalu tidak menimpa (K4).
- Valuation dicatat sebagai nilai baru per tanggal; delta dihitung app, delta 0 ditolak, valuation tidak diedit lewat form transaksi (K5).
- Bucket alokasi maks 2 level; target child relatif ke parent, dibandingkan secara global (K6, K7). Basis porsi = gross aset non-liability `include_in_net_worth`, termasuk akun arsip (K8). Warna chart dari palet `--chart-*` per urutan root; kolom `color` bucket belum dipakai di UI.
- Titik riwayat (net worth, alokasi) = saldo per hari terakhir periode; jumlah periode di-clamp 1..=24 (`MAX_PERIODS`) di Rust dan browser-ledger (K9).
- Breakdown kategori hanya root dengan total > 0, nominal terbesar dulu. Persentase breakdown dihitung UI dari nominal backend (presentasi).
- Chart SVG buatan sendiri (Donut, Bar, Line) tanpa dependensi; label sumbu memakai format ringkas (`11,5 jt`), angka lengkap selalu di tabel di bawah chart (K10).
- Pool koneksi baca tetap ditunda; diukur di benchmark Fase 8 (K11). Dasbor/RPT-01 tetap Fase 7 (K12).
- Target bucket hanya dalam persen (`target_bp`); target nominal (CAP-01 "atau nominal") ditunda ke Fase 7 karena butuh migrasi kolom baru dan aturan campuran persen/nominal.
- E2E Gate 1 (`ui/e2e/budget-allocation.spec.ts`) berjalan terhadap browser-ledger. Cek manual di jendela Tauri (DB nyata) dan pemakaian harian ≥ 1 bulan (Gate 1) belum dilakukan.

## Fase 6 — Keamanan data

- DAT-01: backup manual + otomatis harian via SQLite online backup API, retensi 14 file, backup sebelum setiap migrasi; restore teruji di CI (saldo identik).
- `PRAGMA integrity_check` saat startup bila shutdown sebelumnya tidak normal.
- DAT-02: export CSV/JSON (transaksi, akun, kategori, budget).
- SEC-01: ganti fitur rusqlite `bundled` → `bundled-sqlcipher`; master password (Argon2id), recovery key yang bisa dicetak, auto-lock idle 5 menit, peringatan "tidak ada password recovery". Enkripsi opsional saat onboarding (D8).

**Exit:** force-kill saat menulis tidak menghasilkan saldo korup; DB terenkripsi tidak terbaca tanpa password.

**Fase 6a selesai** (backup, integritas, ekspor; detail K1–K15 di plan 6a):
- Backup di `<data_dir>/backups/` bernama `{kind}-{YYYYMMDD}T{HHMMSS}Z[-N].db`; retensi otomatis 14, pra-migrasi 5, pra-restore 5. Backup manual ke lokasi pilihan user tanpa retensi.
- Backup otomatis jatuh tempo bila belum ada, ≥ 20 jam, atau yang terbaru bertanggal di masa depan; dicek saat start lalu tiap jam.
- Restore: validasi file → backup pra-restore → online backup API ke DB aktif → migrasi → UI reload. File DB aktif (+ `-wal`/`-shm`/`-journal`) ditolak sebagai sumber/tujuan.
- `session.lock` menandai sesi berjalan; bila masih ada saat start, `PRAGMA integrity_check` dijalankan dan backup otomatis dilewati saat gagal. Dialog peringatan di UI.
- Ekspor JSON (`format: "nabungo-export"`, `version: 1`) dan folder CSV baru per ekspor (UTF-8 BOM, CRLF, sel teks yang mirip formula diawali `'`).
- Exit "force-kill tidak merusak saldo" diuji otomatis (`crates/app/tests/crash_consistency.rs`).
- Ditunda: layar pemulihan bila DB gagal dibuka sama sekali → Fase 8 (K9). SEC-01 → plan Fase 6b.

**Fase 6b selesai** (SEC-01, enkripsi opsional):
- SQLCipher (`bundled-sqlcipher`; OpenSSL vendored di Windows). DEK acak dibungkus KEK Argon2id (64 MiB) di `nabungo.key`; recovery key = DEK (Crockford base32, 13×4), dinormalisasi dari huruf kecil/spasi/`O`/`I`/`L`.
- Aktifkan/matikan dari Pengaturan atau saat onboarding (default mati) lewat `sqlcipher_export` + rename atomik; backup ikut dikonversi. Ganti password tanpa mengenkripsi ulang DB. Header file = sumber kebenaran; sisa crash dibersihkan saat start.
- Layar kunci saat start bila DB terenkripsi; kunci otomatis 1/5/10/15/30 menit (default 5) dan "Kunci sekarang"; error `locked` dari command apa pun membawa UI ke layar kunci. Recovery key ditampilkan sekali dengan Salin/Cetak dan peringatan "tidak ada pemulihan password".
- Ditunda: memulihkan backup terenkripsi dari instalasi lain (key file berbeda) → Fase 8 (K9). Checklist manual Tauri (plan 6b, Task 7) dijalankan user.

- TRX-06: recurring rule (`rrule`), transaksi jatuh tempo muncul untuk dikonfirmasi/lewati/edit; layar Terjadwal.
- TRX-08: attachment struk (gambar/PDF) di folder data app, sha256 di DB.
- CAT-04: CRUD tag & payee + autocomplete.

- RPT-01: dasbor lengkap (net worth, cashflow, top 5 kategori, budget hampir habis, terjadwal jatuh tempo, ringkasan alokasi).

Keputusan 7a (rinci di plan 7a, K1–K11):

- Flag rollover per kategori × periode (baris `budget`); bawaan = Σ budget rantai periode ber-flag yang berurutan − realisasi (rollup) rantai itu, boleh negatif, hanya untuk periode yang ber-budget; rantai putus pada periode tanpa budget/flag. Salin budget ikut menyalin flag.
- Level: `warning` bila terpakai ≥ 80% tersedia (budget + bawaan), `exceeded` bila ≥ 100%; tersedia ≤ 0 → `exceeded` bila ada realisasi atau tersedia negatif. Persen dibulatkan ke bawah, `null` bila tersedia ≤ 0.
- Sisa per hari hanya untuk periode berjalan: max(sisa, 0) ÷ hari tersisa (termasuk hari ini).
- Alert hanya saat level naik ke non-`ok` karena create/update transaksi (periode tanggal lama dan baru); ditampilkan sebagai toast di UI.

Keputusan 7b (rinci di plan 7b, K1–K13):

- Tidak ada jenis `payable`: akun `receivable` dipakai untuk Piutang maupun Hutang, arahnya dari tanda saldo (positif = piutang, negatif = hutang dan dihitung sebagai liabilitas). Migrasi tipe akun tidak diperlukan.
- Rekonsiliasi mencatat selisih saldo riil vs tercatat sebagai transaksi penyesuaian, lalu menandai posting akun itu sampai tanggal rekonsiliasi. Mengedit transaksi menghapus tanda reconciled-nya.

Keputusan 7c (rinci di plan 7c):

- Lampiran disimpan sebagai file bernama sha256 di `attachments/` folder data, dengan dedup: file yang sama dipakai bersama; file dihapus saat rujukan terakhirnya hilang (K1/K5).
- Backup manual menyertakan lampiran dalam folder sidecar `<nama-backup>-lampiran/` (K7).
- Lampiran tidak ikut terenkripsi SQLCipher; layar Keamanan menjelaskan hal ini (K9).

Keputusan 7e (rinci di plan 7e, K1–K13):

- Target bucket persen atau nominal. Per tingkat (sesama parent), nominal dipenuhi dulu; bucket persen membagi `max(basis − Σ nominal, 0)`. Basis root = gross aset, basis child = target efektif parent. Tanpa nominal, hasilnya identik dengan aturan Fase 5 (K1/K2).
- Batas Σ ≤ 100% dan peringatan "≠ 100%" hanya menghitung bucket persen; Σ nominal melebihi basis memberi peringatan, bukan error (K4/K5).
- Dasbor menambah kartu Top 5 kategori pengeluaran, Terjadwal jatuh tempo (maks 5, aksi tetap di layar Terjadwal), dan Ringkasan alokasi (bucket root); tiap kartu disembunyikan bila datanya kosong (K7–K10).

## Fase 8 — Hardening & rilis

- Benchmark dengan fixture 50.000 transaksi: startup < 1,5 s, simpan < 100 ms, daftar < 200 ms, laporan < 500 ms; tambahkan `account_balance_daily` hanya bila profiling menunjukkan perlu.
- Aksesibilitas: kontras WCAG AA, ukuran font bisa diubah, audit navigasi keyboard.
- Test firewall: 0 request keluar.
- Packaging: AppImage/.deb/.rpm + NSIS/MSI dari CI; installer < 15 MB; updater mati secara default.

| Sub-fase | Isi | Catatan |

Plan: `2026-10-24-fase-8a-performa.md`, lanjutan `2026-10-24-fase-8a2-performa-lanjutan.md`. **Selesai**: semua skenario S1–S6 dalam budget (plaintext + SQLCipher); `startup_ms` end-to-end belum diukur manual |
| 8b Pemulihan | Layar pemulihan bila DB gagal dibuka (ditunda dari 6a K9); restore backup terenkripsi dari instalasi lain (ditunda dari 6b K9) | Bisa butuh command baru di luar `Ledger` (DB belum terbuka) |

**Exit:** → **Gate 2 / rilis v1**.
